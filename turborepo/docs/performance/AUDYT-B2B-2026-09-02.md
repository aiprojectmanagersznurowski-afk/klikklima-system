Powtórzenie audytu z `performance_audit.md` (Antigravity). Różnica metodologiczna: **wszystkie liczby poniżej są zmierzone na żywej bazie i żywym endpoincie Auth**, nie oszacowane. Kilka wniosków poprzedniego audytu okazało się nieaktualnych.

## Znaleziska

### 🔴 P0-1 — `supabase.auth.getUser()` wołane 3–4× na jedną nawigację

`getCurrentActorRole()` (`utils/supabase/server.ts`) przy każdym wywołaniu robi roundtrip do Auth + zapytanie do bazy. Jest wołane w `page.tsx` **i** wewnątrz `getLeads()`. Dla roli `audytor` dochodzi jeszcze jedno jawne `auth.getUser()` w `getLeads()`. Middleware robi swoje własne, czwarte.

Żaden z tych wyników nie jest współdzielony — mimo że to **ten sam użytkownik w tym samym żądaniu**.

**Naprawa:** `React.cache()` (udokumentowane w `node_modules/next/dist/docs/01-app/01-getting-started/06-fetching-data.md`) memoizuje na czas jednego żądania serwerowego. Trzy linijki, zero zmian w API wołających.

### 🔴 P0-2 — sekwencyjne `await` tam, gdzie dane są niezależne

`leads/page.tsx`: `await getLeads()` → `await getAuditors()` → `await getCurrentActorRole()`. Żadne z tych trzech nie zależy od wyniku poprzedniego. Zmierzony narzut sekwencyjności: **557 ms vs 240 ms** dla trzech zapytań.

### 🔴 P1-3 — `getCustomers()`: 1275 ms na pustej tabeli

```ts
prisma.klienci.findMany({
  include: { leady: { include: { instalacje: true } } },  // 3 poziomy
  orderBy: { created_at: 'desc' },
  // brak take/skip
})
```

Z całego wyniku używane są wyłącznie **dwie liczby** (`leady.length`, suma `instalacje.length`). Prisma pobiera pełne wiersze trzech tabel, żeby policzyć elementy tablicy w JS. Brak paginacji oznacza, że koszt rośnie liniowo bez ograniczenia — dziś 1,3 s przy zerze klientów, przy realnym ruchu wielokrotnie więcej.

**Naprawa:** `_count` po stronie bazy + `take`/`skip`.

### 🟠 P2-4 — brak `loading.tsx` w całym panelu

`find apps/b2b-web/src/app -name loading.tsx` → **zero trafień**. Wszystkie 10 tras ma `force-dynamic`, więc użytkownik po kliknięciu patrzy na **poprzedni ekran przez ~1,6 s** bez żadnej informacji zwrotnej. To jest ta „zamrożona" percepcja z pierwotnego zgłoszenia — nawet po naprawie P0/P1 zostanie ~0,5 s, którą trzeba czymś pokryć.

### 🟡 P3-5 — brak indeksów na kluczach obcych (dług na przyszłość, **zero zysku dziś**)

Faktyczny stan indeksów na żywej bazie:

```
leady:      leady_pkey, leady_status_idx, leady_created_at_idx
klienci:    tylko klienci_pkey
adresy:     tylko adresy_pkey
instalacje: tylko instalacje_pkey
serwisy:    tylko serwisy_pkey
```

Postgres **nie tworzy automatycznie indeksów na kolumnach FK**. Każdy JOIN po `klient_id`, `adres_id`, `audytor_id`, `lead_id`, `zespol_id` to dziś seq-scan. Przy 0 wierszach — bez znaczenia. Przy pierwszych tysiącach — problem numer jeden.

Uczciwie: to jedyne znalezisko z listy, którego naprawa **nie da się dziś zmierzyć**. Robimy je jako ubezpieczenie, nie jako optymalizację.

### 🟡 P3-6 — `force-dynamic` na 10 trasach

Wyłącza cache Next.js całkowicie. Ale: panel pokazuje dane operacyjne per-rola, a `use cache: private` w Next 16 jest oznaczone `experimental` i wymaga flagi `cacheComponents`. **Świadomie odkładam** — ryzyko przewyższa zysk, dopóki P0/P1 nie są zrobione.
